# Resident rewards — staging (KEMP-CHECKINS-REWARDS-01)

## Назначение

Серверный источник истины для начислений резидентам клуба:

- подтверждённая основателем клубная тренировка: **+10 баллов** (по событию и участнику);
- подтверждены БЖЖ + ОФП + кикбоксинг одной недели зачёта: **+10 баллов и +70 коинов** (один раз на неделю);
- исправление решения основателя обращает награды без удаления истории;
- ручные операции с коинами не влияют на баллы и рейтинг;
- перенос сохраняет исходную неделю зачёта (`week_anchor`, уже существует).

## Состав

- `up.sql` — реестр `resident_reward_awards`, пересчёт недели, расширенный
  `founder_confirm_attendance`, `founder_cancel_event_web` (безопасная отмена,
  риск R1), обновлённые `get_resident_checkins_web` (отменённые события с
  отметками остаются в истории) и `get_resident_rating_web` (баллы интенсива +
  активные баллы резидентов), новый `get_resident_rewards_web`.
- `down.sql` — откат: восстанавливает прежние версии функций, удаляет реестр
  наград (записи `coin_transactions` — append-only — сохраняются; правило
  `resident_week_full` деактивируется, но не удаляется ради целостности
  `rule_id` в журнале).
- `test-fixture.sql` — ТОЛЬКО локальный стенд: достраивает схему геймификации
  по `migration-mira-v5` и founder-RPC по `main:sql/resident-checkins/up.sql`;
  `is_kemp_founder` подменён на «любой super_admin стенда».
- `test-acceptance.sql` — последовательные приёмочные сценарии (psql,
  JWT-claims через `set_config`).
- `test-local.sh` — оркестрация + параллельные подтверждения (гонки).
  Отказывается работать с нелокальным `KEMP_TEST_DB_URL`.

## Ключевые решения

1. **Отдельный реестр, не `leaderboard`.** `update_user_leaderboard`
   пересчитывает `leaderboard.total_points` из таблиц активностей интенсива и
   затёр бы резидентские начисления. Рейтинг резидентов считает сумму
   `leaderboard.total_points` + активные баллы реестра — исторические баллы
   интенсива сохраняются, `leaderboard` не перезаписывается.
2. **Правило `training_attendance` (1 коин) не используется и не меняется.**
   Недельный бонус идёт отдельным правилом `resident_week_full` (70) и своими
   `source_type` в `coin_transactions`; двойного начисления не возникает.
3. **Идемпотентность:** уникальные индексы `(user_id, schedule_id)` для
   тренировок и `(user_id, week_start)` для недели; повторное подтверждение —
   `skipped` без новых записей (фильтр `IS DISTINCT FROM` в исходной функции
   сохранён).
4. **Параллелизм:** `SELECT … FOR UPDATE` на событии (уже было) +
   `pg_advisory_xact_lock` на пару (участник, неделя) + уникальные индексы.
5. **Обратимость:** награды не удаляются, а переводятся в `reversed` с
   записью в `history`; коины компенсируются встречной записью −70
   (`resident_week_full_reversal`).
6. **R1:** событие с историей посещений/броней/наград деактивируется
   (`is_active=false`), а не удаляется; FK `schedule_participants.schedule_id`
   имеет `ON DELETE CASCADE` — прямое удаление теряло историю. Читатель
   резидента показывает отменённые события, если по ним есть отметки.
   Регулярные серии не пересоздают отменённые экземпляры — это гарантирует
   ledger `club_recurring_occurrences` (`ON CONFLICT DO NOTHING`).
7. **Исторические данные:** подтверждения, сделанные до включения системы,
   наград не порождают (массовый перерасчёт не выполняется — отдельное
   решение владельца).

## Найдено при сверке (этап A)

- В рабочей БД сигнатуры `founder_confirm_attendance`, `founder_get_event_attendance`,
  `founder_set_event_kind`, `get_resident_checkins_web`, `request_attendance_web`,
  `get_resident_rating_web`, `get_rating_web`, `get_user_coin_balance`,
  `award_coins_by_rule`, `is_kemp_founder` существуют (VERIFIED_LOG, пробы REST
  только чтением, 42501 для anon / 200 для get_user_coin_balance).
- Таблицы `coin_rules`, `coin_transactions`, `leaderboard`, `user_points`,
  `activity_checkins` существуют в рабочей БД (VERIFIED_LOG, REST `limit=0`).
- `get_user_coin_balance(uuid)` исполняема ролью **anon** — любой может узнать
  баланс любого пользователя по UUID. Не блокер этой задачи; зафиксировано как
  отдельное наблюдение для владельца.
- Исходная `get_resident_rating_web` из `sql/web-app-resident.sql` содержит
  обращение к CTE `ranked` вне её оператора — вероятна ошибка выполнения на
  проде при реальном вызове. Новая версия в `up.sql` это исправляет
  (один оператор). Требует проверки при приёмке.

запреты founder-RPC для резидента, RLS реестра.
